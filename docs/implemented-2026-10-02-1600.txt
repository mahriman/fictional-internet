Database changes

The migrations add:

- Projects owned by users, with name and optional description.
- Generated content belonging to a project, with a stable `content_type` key and optional title.
- Structured version content, origin, context snapshot, generation metadata, and caller-supplied version number.

Foreign keys cascade from users through projects and content to versions. Indexes support project/type lookup and enforce a unique version number per content record. No current-version pointer or automatic numbering was added.

The feature tests used the configured in-memory SQLite database. I did not apply migrations to the configured application database.

Architectural decisions

- `NewsArticleType` provides the first stable key (`news_article`), prompt instructions, output schema, and Laravel validation rules.
- `ContentTypeRegistry` resolves definitions by key and throws `InvalidArgumentException` for unknown or duplicate keys.
- Versions reject ordinary Eloquent update and individual delete operations; parent deletion still cascades through the database.
- No `ContentPresenter` or other presentation abstraction was added.
- Version immutability is enforced through Eloquent model events. Direct query-builder updates or event-bypassing APIs could bypass those guards; the application does not add database triggers.
